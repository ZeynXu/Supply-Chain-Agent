# Agent Eval 设计文档评审意见

**评审者视角**: 资深 Agent 系统工程师
**评审对象**: `/root/Supply-Chain-Agent/docs/Agent Eval.md`
**评审日期**: 2026-06-07

---

## 一、核心矛盾问题

### 1.1 LLM Judge 模型选择的自相矛盾

**文档表述**:
> "LLM Judge必须与生成模型使用不同家族以消除家庭偏差"
> "本评估系统将采用智谱GLM-4.7作为Judge评估同一模型的输出"

**质疑**:
这是一个严重的自相矛盾。文档明确指出业界最佳实践是"Judge 必须与生成模型使用不同家族"，却在同一页推荐使用 GLM-4.7 作为 Judge——而生产环境很可能也是使用智谱系列模型。这违反了文档自己引用的原则。

**建议**:
- 若生产使用智谱系列，Judge 应选择其他模型族（如 GPT-4、Claude、或开源 LLaMA 系列经过微调的 Judge 模型）
- 若必须使用同系列模型，需在文档中明确说明这是成本/可用性妥协，并加强人工校准频率（从月度提升至周度）

---

### 1.2 四层架构与现有 Harness 三层架构的关系模糊

**文档表述**:
> "本评估系统是Harness Engineering设计方案中'Layer 2：验证与可观测层'与'Layer 3：反馈与持续改进层'的核心实现部分"

**质疑**:
文档定义了四层评估架构（单元能力层 → 场景验证层 → 线上离线评估层 → 生产持续监控层），但现有 Harness Engineering 已经有三层架构。这导致：

1. **概念重叠**: Harness Layer 2 的 Evals 和新设计的 Layer 1/2/3 如何对应？
2. **代码结构冲突**: 文档新增 `evaluation/` 目录，但现有 `harness/evals/` 已有评估器，两者如何整合？
3. **职责边界不清**: `harness/feedback/cluster_errors.py` 已实现错误聚类，新设计的 Layer 4 是否要重新实现？

**建议**:
- 明确四层评估架构与 Harness 三层架构的映射关系
- 在代码层面明确是扩展现有 `harness/` 还是创建独立的 `evaluation/`
- 避免功能重复实现

---

## 二、数据目标的合理性质疑

### 2.1 测试数据量目标缺乏依据

**文档表述**:
| 数据集 | 数据量目标 |
|--------|------------|
| Golden Dataset | 200+ 黄金标注 |
| 自动生成数据集 | 500+ 变体 |
| 生产回放数据集 | 1000+ 真实 |

**质疑**:
这些数字看起来像是"拍脑袋"决定的：
- 为什么是 200 条而不是 150 或 300？
- 供应链场景 7 种一级意图 × 12 种二级意图 = 84 种组合，200 条黄金数据如何覆盖？
- 自动生成 500 变体的"参数扰动、同义词替换"质量如何保证？

**建议**:
- 基于场景覆盖矩阵计算最小测试集：至少保证每个意图组合有 3 个正向用例 + 2 个异常用例
- 给出数据量推导公式，而非凭空数字
- 自动生成数据集应有质量门控（如人工抽检 10%）

---

### 2.2 采样策略与现有设计冲突

**文档表述**:
> "错误类Trace全量保留，成功类Trace按5%采样"

**现有设计**:
> `HARNESS_TRACE_SAMPLE_RATE=0.01` (1% 采样率)

**质疑**:
采样率从 1% 提升到 5%，这意味着存储成本增加 5 倍。文档未说明：
- 为什么需要 5% 采样？
- 存储成本和查询性能的影响评估？
- 与现有 `harness/observability/trace.py` 的配置如何协调？

**建议**:
- 采样率应作为可配置参数，而非硬编码在设计中
- 进行成本-收益分析，给出采样率的决策依据

---

## 三、资源估算的乐观倾向

### 3.1 人天估算过于乐观

**文档表述**:
| 资源类型 | Phase 1 | Phase 2 | Phase 3（月均） |
|----------|---------|---------|-----------------|
| 开发工程师 | 15人天 | 20人天 | 5人天 |
| 测试工程师 | 10人天 | 15人天 | 8人天 |

**质疑**:
基于实际工程经验，这些估算存在严重的乐观偏差：

1. **Phase 1 (3周)**: 50+ 测试用例设计 + 4 种核心指标模块 + 工具调用准确率 90% 目标，15 开发人天 + 10 测试人天明显不足
2. **LLM Judge 校准**: 月度校准需要人工重新标注、计算 Kappa、调整 Rubric，5 人天/月不够
3. **未计入隐性工作**: 数据清洗、Mock 环境搭建、CI/CD 集成、文档维护

**建议**:
- 参照行业基准，评估工作量通常需要预留 30-50% 缓冲
- 建议将 Phase 1 延长至 4 周，资源估算增加 40%

---

### 3.2 里程碑验收标准存在逻辑问题

**文档表述**:
> M2：评估框架可用 — 可离线运行全套评估，生成Markdown报告
> M3：场景验证完成 — 覆盖所有意图，通过率≥70%

**质疑**:
M2 和 M3 存在依赖关系问题：
- 如果 M2 才"可运行评估"，那 M3 如何能在同一 Phase 内完成场景验证？
- 70% 通过率目标与项目报告中的 72% 任务成功率基线几乎持平，这意味着几乎没有改进空间的要求

**建议**:
- M3 应设定渐进目标：Phase 1 结束时 ≥65%，Phase 2 结束时 ≥75%，最终 ≥85%
- 调整里程碑时间线，确保依赖关系合理

---

## 四、技术实现的具体问题

### 4.1 工具调用正确性评估的权重分配

**文档表述**:
```python
result.score = (
    result.decision_correct * 0.2 +
    result.tool_correct * 0.3 +
    result.params_complete * 0.3 +
    result.params_valid * 0.2
)
```

**质疑**:
权重分配存在问题：
- **决策正确性仅 20%**: 用户闲聊时错误调用工具是严重问题，应给予更高权重
- **参数完整性 30% vs 参数有效性 20%**: 参数格式错误（如 order_id 传字符串而非整数）与参数缺失同等重要

**建议**:
```python
weights = {
    'decision_correct': 0.30,  # 决策错误是致命问题
    'tool_correct': 0.25,      # 工具选择错误导致全链路失败
    'params_complete': 0.25,   # 参数缺失无法执行
    'params_valid': 0.20       # 参数格式错误会导致下游异常
}
```

---

### 4.2 轨迹六维评分的维度遗漏

**文档表述**:
> 六维评分模型：工具选择正确性、参数完整性、参数有效性、执行顺序合理性、审计规则遵循、最终答案可达性

**质疑**:
供应链场景的关键维度被遗漏：
- **错误恢复能力**: 当工具调用失败时，Agent 是否有合理的重试/降级策略？
- **澄清循环效率**: 当参数缺失时，Agent 是否能在 3 轮内完成澄清？
- **响应时间**: 执行效率维度在轨迹评分中未体现

**建议**:
- 扩展为八维或九维评分模型
- 明确各维度在供应链场景下的权重可配置

---

### 4.3 Cohen's Kappa 阈值设定问题

**文档表述**:
> `self.kappa_threshold = 0.7  # Cohen's Kappa阈值`

**质疑**:
Cohen's Kappa = 0.7 代表"高度一致"，但在 LLM 评估场景下：
- LLM Judge 与人类评分的一致性通常在 0.4-0.6 区间
- 强制要求 0.7 可能导致频繁校准失败，增加人工成本

**建议**:
- 初始阈值设为 0.6（中等一致性），逐步提升目标
- 区分不同评分维度：客观维度（如格式正确性）要求 0.8+，主观维度（如帮助性）允许 0.5+

## 五、与现有 Harness 集成的接口问题

### 5.1 接口设计过于模糊

**文档表述**:
```
Harness Evals（已有）         评估系统（本设计）
    │                              │
    ├── validation_set.yaml  ──→  被评估系统消费
    ├── regression_set.yaml  ──→  作为回归测试集执行
    └── 业务规则库 → 用于Auditor验证评估
```

**质疑**:
接口定义不明确：
- `validation_set.yaml` 和 `regression_set.yaml` 在现有 Harness 中不存在，是新增还是复用？
- 现有 `harness/evals/` 下的 9 个评估器如何与新系统集成？
- 数据流向是单向还是双向？

**建议**:
- 明确文件路径：是 `harness/evals/datasets/` 还是 `evaluation/datasets/`
- 定义明确的 API 接口（函数签名或 REST API）
- 提供迁移/集成示例代码

---

### 5.2 功能重复实现风险

**现有 Harness 实现**:
- `harness/feedback/cluster_errors.py`: 错误聚类
- `harness/feedback/weekly_report.py`: 周度报告
- `harness/observability/metrics.py`: Prometheus 指标
- `harness/observability/trace.py`: Trace 收集

**新设计计划实现**:
- Layer 4 生产监控层
- 失败模式聚类
- 监控仪表盘

**质疑**:
多处功能重叠：
- 错误聚类：已有 `cluster_errors.py`，为何新设计要重新实现？
- 周度报告：已有 `weekly_report.py`，与评估系统的报告如何协调？

**建议**:
- 明确复用策略：扩展现有模块 vs 创建新模块
- 避免"重复造轮子"，优先复用 Harness 已有能力

## 六、总结与建议优先级

### P0 - 必须修改
1. 修正 LLM Judge 模型选择的矛盾，或明确说明妥协理由
2. 明确与现有 Harness 架构的关系，避免概念混乱
3. 重新估算资源投入，增加缓冲

### P1 - 强烈建议
4. 数据量目标应基于场景覆盖计算，而非凭空设定
5. 调整评分权重分配，提高决策正确性的权重
6. 补充错误恢复、澄清效率等关键评估维度

### P2 - 建议优化
7. 明确与 Harness 的接口定义，提供示例代码
8. 调整 Cohen's Kappa 阈值为渐进目标
9. 统一采样率配置，避免与现有设计冲突

---

**评审结论**: 
Agent Eval.md 文档在评估体系设计上具有较好的理论框架，但存在多处自相矛盾、估算过于乐观、与现有系统关系模糊等问题。建议在正式实施前进行修订，确保设计的可行性和与现有 Harness Engineering 的协同性。
